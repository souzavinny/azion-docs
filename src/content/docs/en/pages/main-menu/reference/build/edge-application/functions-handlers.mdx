A handler is the entry point a function exposes to [Azion Runtime](/en/documentation/runtime/overview/). [Functions](/en/documentation/build/functions/) supports two handlers: `fetch`, which answers an HTTP request with a response, and `firewall`, which decides whether a request continues. You declare both with the ES Modules pattern or with the Service Worker pattern.

## Handler patterns

Functions supports two ways to declare a handler. In the ES Modules pattern, the function exports a default object and each handler is a property of that object. In the Service Worker pattern, the function registers each handler on an event with `addEventListener`. Azion recommends the ES Modules pattern, and maintains the Service Worker pattern for backward compatibility.

| Pattern | Status | Declaration | Blocks a request with |
| --- | --- | --- | --- |
| ES Modules | Recommended | A property of the object in `export default` | `ctx.deny()` |
| Service Worker | Legacy | `addEventListener('fetch', handler)` and `addEventListener('firewall', handler)` | `event.deny()` |

Both patterns accept the same two handler names. A function that declares both handlers runs `firewall` first, and reaches `fetch` only for the requests `firewall` does not block.

## `fetch` handler

The `fetch` handler answers an HTTP request. It receives the request, the environment, and the execution context, and it returns a `Response`. When the function also declares a `firewall` handler, `fetch` runs only for the requests that `firewall` allows through.

Declare a `fetch` handler in the ES Modules pattern:

<Code lang="javascript" code={`
export default {
  fetch: async (request, env, ctx) => {
    return new Response('Hello World');
  }
};
`} />

The `fetch` handler takes these parameters:

| Parameter | Type | Description |
| --- | --- | --- |
| `request` | `Request` | The incoming HTTP request object |
| `env` | `Object` | Environment variables and bindings |
| `ctx` | `Object` | Execution context |
| `ctx.waitUntil(promise)` | `Function` | Extends the lifetime of the function so an asynchronous task finishes after the response returns |

For the environment variables a function reads through `env`, refer to [Environment variables](/en/documentation/products/functions/environment-variables/).

## `firewall` handler

The `firewall` handler decides whether a request continues. It receives the same three parameters as the `fetch` handler. Call `ctx.deny()` to block the request immediately. When the handler returns without calling `ctx.deny()`, the request continues to the `fetch` handler.

Declare a `firewall` handler beside a `fetch` handler in the same default export:

<Code lang="javascript" code={`
export default {
  fetch: async (request, env, ctx) => {
    return new Response('Access granted');
  },

  firewall: async (request, env, ctx) => {
    const userAgent = request.headers.get('User-Agent');

    if (userAgent && userAgent.includes('bot')) {
      ctx.deny();
      return;
    }

    return;
  }
};
`} />

The `firewall` handler takes these parameters:

| Parameter | Type | Description |
| --- | --- | --- |
| `request` | `Request` | The incoming HTTP request object |
| `env` | `Object` | Environment variables and bindings |
| `ctx` | `Object` | Execution context |
| `ctx.deny()` | `Function` | Blocks the request immediately. Available in the ES Modules pattern only. When it is not called, the request continues to the `fetch` handler |

## Service Worker event handlers

The Service Worker pattern registers each handler on an event instead of exporting it. Functions supports the `fetch` and `firewall` events for backward compatibility with existing functions. A `fetch` listener returns its response through `event.respondWith()`, and a `firewall` listener blocks a request through `event.deny()`.

Declare both handlers in the Service Worker pattern:

<Code lang="javascript" code={`
addEventListener('fetch', (event) => {
  event.respondWith(handleRequest(event.request));
});

addEventListener('firewall', (event) => {
  event.deny();
});

async function handleRequest(request) {
  return new Response('Hello World');
}
`} />

A Service Worker event carries these properties and methods:

| Property | Description |
| --- | --- |
| `event.request` | The incoming HTTP request object |
| `event.respondWith(response)` | Returns the response for a `fetch` event |
| `event.continue()` | Finishing outcome for a `firewall` event. Lets the request continue |
| `event.deny()` | Finishing outcome for a `firewall` event. Ends the request with `403 Forbidden` |
| `event.drop()` | Finishing outcome for a `firewall` event. Ends the request without returning a response to the client |
| `event.waitUntil(promise)` | Extends the lifetime of the function so an asynchronous task finishes after the response returns |

**A Service Worker `firewall` handler must reach a finishing outcome.** Every function on Firewall written in this pattern ends in `event.continue()`, `event.deny()`, or `event.drop()`. This differs from the ES Modules pattern, where a handler that returns without calling `ctx.deny()` lets the request continue by omission.

## Asynchronous work with `waitUntil`

`ctx.waitUntil(promise)` extends the lifetime of the function so an asynchronous task finishes after the handler returns its response. Pass it a promise. Use it for work the response does not depend on, such as writing a log entry. The task does not block the response.

Extend the lifetime of a `fetch` handler with `waitUntil`:

<Code lang="javascript" code={`
export default {
  fetch: async (request, env, ctx) => {
    ctx.waitUntil(logRequest(request));

    return new Response('Hello World');
  }
};

async function logRequest(request) {
  console.log(\`Request to: \${request.url}\`);
}
`} />

## Migration from Service Worker to ES Modules

A function written in the Service Worker pattern moves to ES Modules construct by construct. The event listener becomes a property of the default export, and `event.request` becomes the `request` parameter. The handler returns its response, and does not call `event.respondWith()`.

| Service Worker | ES Modules |
| --- | --- |
| `addEventListener('fetch', handler)` | The `fetch` property of the default export |
| `addEventListener('firewall', handler)` | The `firewall` property of the default export |
| `event.request` | The `request` parameter |
| `event.respondWith(response)` | `return response` |
| `event.deny()` | `ctx.deny()` |

A firewall check that blocks bot traffic, in the Service Worker pattern:

<Code lang="javascript" code={`
addEventListener('fetch', (event) => {
  event.respondWith(handleRequest(event.request));
});

addEventListener('firewall', (event) => {
  const userAgent = event.request.headers.get('User-Agent');

  if (userAgent && userAgent.includes('bot')) {
    event.deny();
    return;
  }
});

async function handleRequest(request) {
  return new Response('Hello World');
}
`} />

The same check in the ES Modules pattern:

<Code lang="javascript" code={`
export default {
  fetch: async (request, env, ctx) => {
    return new Response('Hello World');
  },

  firewall: async (request, env, ctx) => {
    const userAgent = request.headers.get('User-Agent');

    if (userAgent && userAgent.includes('bot')) {
      ctx.deny();
      return;
    }

    return;
  }
};
`} />

## Unsupported patterns

Functions does not support a module that declares its handler in any other shape. A default export that is a function, a named `fetch` export, and a file with no export are all unsupported.

<Code lang="javascript" code={`
// Not supported: a function exported directly as the default export.
export default function(request) {
  return new Response('Hello');
}

// Not supported: a named export.
export function fetch(request) {
  return new Response('Hello');
}

// Not supported: no export.
function handleRequest(request) {
  return new Response('Hello');
}
`} />

A function that matches none of the supported patterns raises the error `Unsupported handler pattern detected`. To resolve it, rewrite the function with the ES Modules pattern, or with the Service Worker pattern as a temporary measure.


## Request metadata

A function that runs on [Firewall](/en/documentation/secure/firewall/) reads request metadata from the `metadata` property of the request object. The metadata carries GeoIP values, the remote client address and port, and the server protocol. It also carries TLS ciphers and fingerprints, and identifiers for the account, the function instance, and the request. Use it to filter access to an application, or to apply different logic per request.

Inside a Service Worker firewall handler, read the remote client address:

<Code lang="javascript" code={`
let ip = event.request.metadata["remote_addr"];
`} />


For the complete list of metadata names, refer to [Metadata API](/en/documentation/products/applications/functions/runtime/api-reference/metadata/).
