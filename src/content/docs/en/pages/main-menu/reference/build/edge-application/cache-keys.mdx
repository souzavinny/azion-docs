A cache key is the index entry for an object stored by [Cache](/en/documentation/build/cache/) on Azion edge nodes. When a request reaches an application for the first time, the edge node forwards it to the origin server. It then generates a cache entry for each object it receives. When a later request produces a cache key that matches a stored entry, the edge node answers from cache. The request never reaches the origin server.

By default, Azion treats each URL as a distinct object in cache. [Application Accelerator](/en/documentation/build/application-accelerator/), [Image Processor](/en/documentation/build/image-processor/), [Device Groups](/en/documentation/build/applications/reference/device-groups/), and Large File Optimization append variations to the key. A single URL can then index several stored objects.

---

## Cache key format

The default cache key format concatenates the following elements of the request URI, in this order:

- Scheme of the request
- Host
- Path to the resource
- Query strings
- A variation separator and, when implemented, the appended variations

An object with the URI `https://static.example.com/page/site.js` generates the cache key `httpsstatic.example.com/page/site.js`. The scheme and the host are joined directly, with no `://` between them.

Cache keys are case sensitive, which means upper and lower case characters are considered distinctive.

Some cache keys change with the variations generated on Azion edge nodes. When variations are enabled, the cache key can contain the `@@` separator at the end, which results in `httpsstatic.example.com/page/site.js@@`.

## Cache key variations

Each variation appends to the default cache key format instead of replacing it. One object can hold several cache keys at the same time.

| Variation | What it adds to the key | Requires |
| --- | --- | --- |
| Request method | The method, at the start of the key | None |
| Image format and processing | The `?` separator with the processing arguments, then `@@` and the format | Image Processor |
| Device group | `@@` and the device group name | Device Groups, with Adaptive Delivery set to vary by device group |
| Cookie | `@@`, the cookie names and values, then `;` | Application Accelerator |
| Query string | The query separator and the selected arguments | Application Accelerator |
| File fragment | `@@bytes=` and the byte range of the fragment | Large File Optimization |
| Request body | `@@` and the MD5 hash of the body | Application Accelerator |

## Complex requests

A complex request is any request whose method is not `GET` or `HEAD`. When the resource is obtained through a complex request, the method is added to the start of the cache key.

For an `OPTIONS` request, the cache key generated for an object is `optionshttpsstatic.example.com/page`.

## Image Processor

[Image Processor](/en/documentation/build/image-processor/) manipulates images through the `ims` query string. When the module is active, the `ims` query string becomes part of the cache key. A variation converted to another format also carries the file format after the separator.

The key for a processed image holds the host, the path, and the `?` separator. It then holds the key-value pairs for the type of processing, and the `@@` separator for the image format variation the browser supports.

An image at `https://static.example.com/static/images/image.jpg` can hold these cache keys:

- `httpsstatic.example.com/static/images/image.jpg@@`
- `httpsstatic.example.com/static/images/image.jpg@@webp`
- `httpsstatic.example.com/static/images/image.jpg?ims=88x@@`
- `httpsstatic.example.com/static/images/image.jpg?ims=88x@@webp`

Image Processor reads the `ims` field, so an allowlist configured in [Cache by Query String](/en/documentation/build/cache/reference/cache-settings/#cache-by-query-string) must include `ims`.

## Device Groups

[Device Groups](/en/documentation/build/applications/reference/device-groups/) sorts requests into groups by matching the `User-Agent` header against a regular expression. When an object varies per device group, the cache key is appended with the `@@` separator and the device group name.

For an application that implements a variation for the `Mobile` group, the generated cache key is `httpwww.example.com/@@Mobile`.

Device-based variations stay in cache only when [Adaptive Delivery](/en/documentation/build/cache/reference/cache-settings/#adaptive-delivery) is set to vary by device group.

## Advanced Cache Key

[Advanced Cache Key](/en/documentation/build/cache/reference/cache-settings/#advanced-cache-key) segments the cache key by cookies and by query strings. The [Application Accelerator](/en/documentation/build/application-accelerator/) module enables it. Both fields are case-sensitive: they treat uppercase and lowercase letters differently when caching objects.

**Cache by Cookie** generates a cache key variation with the determined cookie names and values, followed by `;`. Content variation based on the `user` cookie can generate these cache keys:

- `httpwww.example.com/@@;`
- `httpwww.example.com/@@user=user;`

**Cache by Query String** generates cache keys with the query separator and the determined arguments. The order follows the query strings submitted in the request. Content variation based on `name` and `city` can generate these cache keys:

- `httpstatic.example.com/page?name=name`
- `httpstatic.example.com/page?city=city&name=name`
- `httpstatic.example.com/page?name=name&city=city`

When **Query string sort** is enabled, multiple query strings are grouped under the same cache key and ordered alphabetically. The position of the fields in the request then stops affecting the key.

## Large File Optimization

[Large File Optimization](/en/documentation/build/cache/reference/cache-settings/#large-file-optimization) breaks a large file into fragments, and each fragment carries a different cache key. For a fragmented object, the cache key appends the `@@bytes=` separator for each piece of content.

For a file that is `2097151` bytes in size, the cache keys generated are:

- `httpstatic.example.com/media/file.mp4@@bytes=0-1048575`
- `httpstatic.example.com/media/file.mp4@@bytes=1048576-2097151`

The default fragment size is 1,024 kB, so the number of keys grows with the size of the file.

## Cached HTTP methods

By default, Azion caches `GET` and `HEAD` requests only. The [Application Accelerator](/en/documentation/build/application-accelerator/) module adds caching for `POST` and `OPTIONS` requests, and both options require the request body to be part of the cache key.

For a cached `POST` or `OPTIONS` request, the cache key appends the `@@` separator followed by the MD5 hash of the request body:

- `httpsdynamic.example.com/path@@md5_of_post_arguments`
- `httpsdynamic.example.com/path@@md5_of_options_arguments`

To turn caching on for these methods, refer to [Caching HTTP methods](/en/documentation/build/cache/reference/cache-settings/#caching-http-methods).

## Cache key headers

An application returns the cache key of the object it served. Request the content URI with the Azion debug header `Pragma: azion-debug-cache`, and the response carries the `X-Cache-Key` header with the cache key value:

```bash
X-Cache-Key: httpsexample.com/resource-path/image.jpeg@@
```

| Header | Value |
| --- | --- |
| `X-Cache-Key` | Cache key of the object |
| `X-Cache-File` | Cache file of the object, consisting of the MD5 of the cache key |

Azion generates the cache key when the origin response is stored on the edge node, and adds it to the `X-Cache-Key` header of the response. The same value is recorded as the `Cache Key` field in Real-Time Events and as `cacheKey` in the GraphQL API.

To read these headers in a browser, refer to [Verify cache indicators in the browser](/en/documentation/build/cache/guides/check-page-cache-time/).

## Cache key purge

[Real-Time Purge](/en/documentation/build/cache/reference/real-time-purge/) accepts a list of cache keys as an argument. Each key expires one variation of an object, so purging every variation means listing every key. A [wildcard purge](/en/documentation/build/cache/reference/real-time-purge/#wildcard-purge) covers them in one request: `@@*` at the end matches cookie-based variations, and `?*` at the end matches query string variations.

A [URL purge](/en/documentation/build/cache/reference/real-time-purge/#url-purge) converts each URL to its cache key without considering content variation in the same URL.

:::caution
Content variations based on cookies, device groups, or image format do not expire with a URL purge. Use a cache key purge or a wildcard purge for these objects.
:::

A purge accepts a URL or cache key of up to 4,096 characters. The [Azion CLI](/en/documentation/products/azion-cli/overview/) takes the list through the `--cachekey` flag.
