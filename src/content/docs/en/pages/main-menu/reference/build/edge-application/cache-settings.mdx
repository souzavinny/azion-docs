A cache setting is the configuration object that decides how [Cache](/en/documentation/build/cache/) stores and serves a response on Azion edge nodes. One setting holds the browser and CDN expiration policies, the cache key variations, and the switches for stale cache, large file optimization, and [Tiered Cache](/en/documentation/build/cache/tiered-cache/). A cache setting changes nothing on its own: a [Rules Engine](/en/documentation/build/applications/reference/rules-engine/) rule applies it with the **Set Cache Policy** behavior.

Several fields require the [Application Accelerator](/en/documentation/build/application-accelerator/) module. Without it, Azion caches only `GET` and `HEAD` requests, the minimum CDN TTL stays at 60 seconds, and the Advanced Cache Key fields are unavailable.

## Cache setting fields

These are the attributes a cache setting accepts in the JSON file passed to `azion create cache-setting` and `azion update cache-setting`. The Cache Settings API groups the same settings under `browser_cache` and `modules`.

| Attribute | Configures | Accepted values | Default |
| --- | --- | --- | --- |
| `name` | The name of the cache setting | String | — |
| `browser_cache_settings` | Browser expiration behavior | `honor`, `override` | `honor` |
| `browser_cache_settings_maximum_ttl` | Browser TTL in seconds, when the behavior is `override` | Integer, in seconds | — |
| `cdn_cache_settings` | Expiration behavior on Azion edge nodes | `honor`, `override` | `honor` |
| `cdn_cache_settings_maximum_ttl` | TTL in seconds on Azion edge nodes, when the behavior is `override` | `60` to `31536000` | `60` |
| `cache_by_query_string` | Query string variation of the cache key | `ignore`, `whitelist`, `blacklist` | `ignore` |
| `query_string_fields` | Query string fields listed for `whitelist` or `blacklist` | Array of strings | — |
| `enable_query_string_sort` | Alphabetical ordering of query string fields before the cache key is built | `true`, `false` | `false` |
| `cache_by_cookies` | Cookie variation of the cache key | `ignore`, `whitelist`, `blacklist` | `ignore` |
| `cookie_names` | Cookie names listed for `whitelist` or `blacklist` | Array of strings | `null` |
| `adaptive_delivery_action` | Device group variation of the cache key | `ignore`, `whitelist`, `blacklist` | `ignore` |
| `device_group` | Device group IDs listed for the adaptive delivery action | Array of IDs | `[]` |
| `enable_caching_for_post` | Caching of `POST` requests | `true`, `false` | `false` |
| `enable_caching_for_options` | Caching of `OPTIONS` requests | `true`, `false` | `false` |
| `enable_stale_cache` | Delivery of expired objects when revalidation fails | `true`, `false` | `true` |
| `is_slice_configuration_enabled` | Large File Optimization | `true`, `false` | `false` |
| `is_slice_edge_caching_enabled` | Large File Optimization on the cache layer | `true`, `false` | `false` |
| `is_slice_l2_caching_enabled` | Large File Optimization on the Tiered Cache layer | `true`, `false` | `false` |
| `slice_configuration_range` | Fragment size in kB for Large File Optimization | `1024` | `1024` |
| `l2_caching_enabled` | Tiered Cache | `true`, `false` | `false` |
| `l2_region` | Tiered Cache region | `na-united-states`, `sa-brazil` | `na-united-states` |

## Browser Cache Settings

**Browser Cache Settings** decides how long a browser keeps a response before it requests the object again. Azion sends the decision to the browser through the `Cache-Control` and `Expires` response headers.

| Option | Value | Behavior |
| --- | --- | --- |
| Honor Origin Cache Headers | `honor` | Azion sends the browser the same `Cache-Control` and `Expires` headers the origin servers sent. |
| Override Cache Settings | `override` | Azion replaces the origin definitions with the TTL set in `browser_cache_settings_maximum_ttl`. |

The `max-age` directive in `Cache-Control` determines the TTL. When `Cache-Control` is absent from the request or the response, the timestamp in the `Expires` header determines it instead. In Azion Console, the override value goes in the **Max Age (seconds)** field.

## CDN Cache Settings

**CDN Cache Settings** decides how long Azion edge nodes keep a response in cache. It governs the copy stored on Azion's distributed network, not the copy a browser stores.

| Option | Value | Behavior |
| --- | --- | --- |
| Honor Origin Cache Headers | `honor` | Azion keeps the cache definitions the origin servers sent through the `Cache-Control` and `Expires` headers. |
| Override Cache Settings | `override` | Azion replaces the origin definition with the TTL set in `cdn_cache_settings_maximum_ttl`. |

The TTL accepts values from `60` to `31536000` seconds (one year) and defaults to `60` seconds. With the [Application Accelerator](/en/documentation/build/application-accelerator/) module active, the minimum drops to `0` seconds. With [Tiered Cache](/en/documentation/build/cache/tiered-cache/) active, a policy that keeps content in the tiered layer needs a TTL of at least `3` seconds.

A TTL of `0` is not the same as a cache bypass. For the difference, refer to [Bypass Cache](/en/documentation/build/applications/reference/rules-engine/#bypass-cache).

## Stale Cache

**Stale Cache** lets Azion edge nodes serve an expired object instead of an error page, while a fresh copy is fetched from the origin. The switch is on by default. A response served this way carries the `STALE` cache status.

Azion reuses a stored response when a revalidation attempt fails because of:

- 5xx errors returned by the origin.
- Connection time-outs or origin unreachability.
- Invalid or missing cache-control headers.
- The object being updated, with revalidation in progress.

The length of the stale window depends on the expiration option. Under **Honor Origin Cache Headers**, the `stale-while-revalidate=<ttl>` directive supplied by the origin sets the window. Under **Override Cache Settings**, or when the origin omits the directive, Azion applies a default window of 300 seconds (5 minutes). During the window the edge node serves the expired copy immediately and fetches a fresh version in the background.

## Large File Optimization

**Large File Optimization** splits a large file into fragments and caches each fragment on demand, at the moment the user requests it. Fragments are delivered gradually as the user consumes the data, which avoids a single large transfer that a timeout or a dropped connection can interrupt. The default fragment size is `1024` kB. To change the fragmentation range, [contact the Sales team](https://www.azion.com/en/contact-sales/).

Each fragment within the defined range carries a different cache key: the key gains the `@@bytes=` separator and the byte range of the fragment. For the key format, refer to [Cache keys](/en/documentation/build/cache/reference/cache-keys/#large-file-optimization).

Large File Optimization applies to the cache layer on Azion edge nodes, and to the tiered layer when [Tiered Cache](/en/documentation/build/cache/tiered-cache/) is an active module. In Azion Console, the cache layer is selected by default when the switch is turned on.

## Advanced Cache Key

**Advanced Cache Key** adds request metadata to the cache key, so one URL can hold more than one cached object. By default Azion treats each URL as a distinct object and ignores the metadata. Two option families carry the feature, and an application can use both at once:

- **Cache by Query String**, on the fields of the query string.
- **Cache by Cookie**, on the name and value of cookies.

Both fields are case sensitive, so uppercase and lowercase letters produce different cached objects. Advanced Cache Key requires the [Application Accelerator](/en/documentation/build/application-accelerator/) module. For the resulting key format, refer to [Cache keys](/en/documentation/build/cache/reference/cache-keys/#advanced-cache-key).

## Cache by Query String

**Cache by Query String** decides which query string fields of a URL differentiate objects in the Azion cache. The listed fields go in `query_string_fields`, and field names are case sensitive.

| Option | Value | Cache key effect |
| --- | --- | --- |
| Content does not vary by Query String (Improves Caching) | `ignore` | The cache key ignores the query string. Two URLs that differ only by the query string are the same object. |
| Content varies by some Query String fields (Whitelist) | `whitelist` | Only the listed fields differentiate objects. All other fields are ignored. |
| Content varies by Query String, except for some fields (Blocklist) | `blacklist` | The listed fields are ignored. All other fields differentiate objects. |
| Content varies by all Query String fields | — | The cache key considers every field. Two URLs that differ by the query string are two objects. |

With `ignore`, `http://example.com/path?queryA` and `http://example.com/path?queryB` deliver the same cached content. Under **Content varies by all Query String fields**, the same two URLs are stored as separate objects.

With `whitelist` and the `city` field listed, `http://example.com/path?city=A&name=X` and `http://example.com/path?city=A&name=Y` are one object, while `http://example.com/path?city=A&name=X` and `http://example.com/path?city=B&name=X` are two.

With `blacklist` and the `random` field listed, `http://example.com/path?city=A&random=123` and `http://example.com/path?city=A&random=456` are one object, while `http://example.com/path?city=A&random=123` and `http://example.com/path?city=B&random=123` are two.

The **Query String Sort** switch, `enable_query_string_sort`, orders every field of the query string before the cache key is built. The position of the fields then stops affecting the key. Turn the switch off when the position of the fields differentiates your content.

## Cache by Cookie

**Cache by Cookie** decides which cookies differentiate objects in the Azion cache, by name and value. The listed cookies go in `cookie_names`, and cookie names are case sensitive.

| Option | Value | Cache key effect |
| --- | --- | --- |
| Content does not vary by Cookies (Improves Caching) | `ignore` | Objects are differentiated by URL alone. Cookies are not considered. |
| Content varies by some Cookies (Allowed Rules) | `whitelist` | Only the listed cookies differentiate objects. All other cookies are ignored. |
| Content varies by Cookies, with the exception of a few (Blocklist) | `blacklist` | The listed cookies are ignored. All other cookies are considered. |
| Content varies by all Cookies | — | Every cookie is considered, in addition to the URL. |

Azion recommends `whitelist` for an application that uses cookies to manage user sessions. It segments the cache by the cookies the application names and ignores every other cookie. Use cookie variation to segment content by user profile, browsing session, or access region.

## Caching HTTP methods

Azion caches `GET` and `HEAD` requests. The **Enable caching for POST** switch, `enable_caching_for_post`, extends caching to `POST` requests, and the **Enable caching for OPTIONS** switch, `enable_caching_for_options`, extends it to `OPTIONS` requests. Both are off by default, and both require the [Application Accelerator](/en/documentation/build/application-accelerator/) module, which also adds support for the `PUT`, `PATCH`, and `DELETE` methods.

Both options require the request body to be part of the cache key. The key of a cached `POST` or `OPTIONS` request gains the `@@` separator followed by the MD5 hash of the body. For the key format, refer to [Cache keys](/en/documentation/build/cache/reference/cache-keys/#cached-http-methods).

While caching for `POST` is off, a `POST` request is restricted from caching and no cache status is logged for it. Refer to [How Cache works](/en/documentation/build/cache/how-it-works/#cache-status) for the full list of statuses.

## Adaptive Delivery

**Adaptive Delivery** varies the cached object by the device group that matched the request. Device groups are created in [Device Groups](/en/documentation/build/applications/reference/device-groups/), which matches a regular expression against the `User-Agent` header of the request.

The `adaptive_delivery_action` field accepts `ignore`, `whitelist`, and `blacklist`, and it defaults to `ignore`. With `ignore`, every device receives the same version of the content, whatever the detection returns. With `whitelist`, Azion keeps one cached object per device group listed in `device_group`. The Azion Console label for that value is **Content varies by some Device Groups (Whitelist)**. The cache key then gains the `@@` separator and the device group name.
