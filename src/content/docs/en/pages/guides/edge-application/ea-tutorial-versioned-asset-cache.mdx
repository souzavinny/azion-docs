In this tutorial, you will cache a versioned JavaScript asset at the edge for one year and release its replacement. You will create a cache setting, apply it with a rule, release a new version, and purge the old one.

The asset is named `app_1.js` and its replacement is named `app_2.js`. Versioning the object name makes each update a new object at the edge, so a one-year TTL never serves a retired build.

---

## Prerequisites

- Access to [Azion Console](/en/documentation/account/guides/how-to-access-azion-console/).
- An application on Azion Platform, reachable at a domain, that serves a static file at `/assets/app_1.js`.
- The [Cache quickstart](/en/documentation/build/cache/quickstart/) completed, which covers your first cache setting and rule.

---

## 1. Create a cache setting with a one-year TTL

A cache setting holds the cache expiration policies of an application. This one keeps versioned assets at the edge for the maximum edge TTL.

To create the cache setting:

1. Access [Azion Console](https://console.azion.com/) > **Applications**.
2. Select the application that serves the asset.
3. Go to the **Cache Settings** tab.
4. Select **+ Cache Setting**.
5. Enter `Versioned assets - 1 year` as the name.
6. In the **Cache Expiration Policies** section, under **Cache Settings**, select **Override Cache Settings**.
7. In **Maximum TTL**, enter `31536000`.
8. Select **Save**.

The cache settings page lists `Versioned assets - 1 year`.

:::note
The edge TTL takes a value between `60` and `31536000` seconds, which is 1 year. With the **Application Accelerator** module active, the minimum is `0`.
:::

## 2. Apply the cache setting to the asset path

A cache setting stays inactive until a rule references it. A rule in the [Rules Engine](/en/documentation/build/applications/reference/rules-engine/) applies the setting to every request under the `/assets/` path.

To create the rule:

1. Go to the **Rules Engine** tab of your application.
2. Select **+ Rule**.
3. Enter `Versioned assets` as the name.
4. Select **Request Phase**.
5. In the **Criteria** section, select the `${uri}` variable.
6. As a comparison operator, select **starts with**.
7. As an argument, enter `/assets/`.
8. In the **Behaviors** section, select **Set Cache Policy**.
9. Select the `Versioned assets - 1 year` cache setting.
10. Select **Save**.

The rule applies the one-year TTL to every request under `/assets/`, including versions of the asset that do not exist yet. Changes can take a few minutes to propagate. On an unexpected response, wait and retry before diagnosing.

## 3. Verify the cache status of the asset

The `X-Cache` response header carries the cache status of a request. The edge returns it when the request carries the `Pragma: azion-debug-cache` debug header.

Request the asset with the debug header:

<Code lang="bash" code={`curl -s -D - -o /dev/null -H "Pragma: azion-debug-cache" "https://<your-azion-domain>/assets/app_1.js"`} />

The response carries the cache status, the IP of the edge node, and the protocol used in the request:

```text
X-Cache: HIT from 200.000.000.00 with HTTP/2.0
```

A `HIT` means the edge served `app_1.js` from the cache. A `MISS` means the edge fetched it from the origin, so send the request again to get a `HIT`.

---

## 4. Release the next version of the asset

A release publishes a new object instead of overwriting the cached one. The rule created in Apply the cache setting to the asset path already covers the new version, because its criteria match the whole `/assets/` path.

To release the new version:

1. Upload the new build to your origin as `/assets/app_2.js`.
2. Update the pages that reference `/assets/app_1.js` to reference `/assets/app_2.js`.

Request the new asset with the debug header:

<Code lang="bash" code={`curl -s -D - -o /dev/null -H "Pragma: azion-debug-cache" "https://<your-azion-domain>/assets/app_2.js"`} />

The first request returns a `MISS`, because the edge holds no copy of `app_2.js` and fetches it from the origin. A second request returns a `HIT`.

## 5. Purge the retired version

The one-year TTL keeps `app_1.js` at the edge long after the release. **Real-Time Purge** removes the retired object without waiting for it to expire.

To purge the retired asset:

1. Access [Azion Console](https://console.azion.com/) > **Products Menu** > **Real-Time Purge**.
2. Select **New Purge**.
3. Fill in the required fields with **Cache** as the layer and `<your-azion-domain>/assets/app_1.js` as the URL to purge.
4. Select **Purge**.

Azion Console confirms the purge and queues it for execution. The purge appears in the history once it completes, because results take time to propagate to all edge nodes.

To retire a whole build directory in one operation, refer to [Wildcard purge](/en/documentation/build/cache/reference/real-time-purge/#wildcard-purge).

## 6. Verify that the retired version left the cache

A purged object is no longer stored at the edge, so the next request for it reaches the origin and reports a `MISS`.

Request the retired asset with the debug header:

<Code lang="bash" code={`curl -s -D - -o /dev/null -H "Pragma: azion-debug-cache" "https://<your-azion-domain>/assets/app_1.js"`} />

The response reports the new cache status:

```text
X-Cache: MISS from 200.000.000.00 with HTTP/2.0
```

Purge results take time to propagate to all edge nodes. On a `HIT`, wait and retry before diagnosing.

The application serves `/assets/app_2.js` from the edge with a one-year TTL, and the retired `app_1.js` no longer occupies the cache.
